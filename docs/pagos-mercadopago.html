Integración de Mercado Pago

Nightowl · Marketplace (split de pagos) con Checkout Pro · plan de trabajo, 6 de noviembre de 2026

Cómo funciona

Cada boliche conecta su propia cuenta de Mercado Pago. Las ventas se cobran con el token del boliche y Nightowl se queda con su comisión mediante marketplace_fee. La plata de las entradas nunca pasa por Nightowl.

El boliche toca "Conectar Mercado Pago" en el panel y autoriza (OAuth). Guardamos su token.
El comprador reserva (10 min) y toca Pagar. Creamos una preferencia con el token del boliche + marketplace_fee.
El comprador paga en Mercado Pago (tarjeta de crédito, débito o dinero en cuenta).
Mercado Pago avisa por webhook. Consultamos el pago y llamamos a confirmPayment: se emiten las entradas con QR y se manda el email.
Mercado Pago descuenta su comisión al boliche y deposita la de Nightowl en nuestra cuenta.

Lo que ya está hecho

  • orders ya tiene payment_provider, payment_reference (únicos juntos), commission_amount y el estado refund_pending (migración 008).
  • confirmPayment (backend/src/checkout.mjs) no duplica entradas si el aviso se repite, rechaza montos que no coinciden y deja para devolver los pagos que llegan tarde sin lugar.
  • simulatePayment y checkoutEnabled (src/lib/checkout.ts) son lo que se reemplaza o se enciende.

Decisiones antes de arrancar

TemaRecomendación
Quién paga el cargo de servicioDefinirlo ya. Si lo paga el comprador, hay que sumarlo al total de la orden; si no, confirmPayment rechaza el pago por monto distinto.

Pasos

  1. Crear la app en Mercado Pago Developers lo hacés vos

    • Entrar a Tus integraciones con la cuenta de Mercado Pago de Nightowl y crear una aplicación de Checkout Pro.
    • Cargar la URL de redirección de OAuth (fija), por ejemplo https://www.nightowl.com.ar/api/mp/oauth/callback.
    • En Webhooks → Configurar notificaciones: URL de producción https://www.nightowl.com.ar/api/webhooks/mercadopago, evento Pagos (y Vinculación de aplicaciones para enterarnos si un boliche se desconecta). Al guardar se genera la clave secreta.
    • Crear usuarios de prueba: uno vendedor (hace de boliche) y uno comprador.
    • Cargar en Vercel y en .env.local: 
      MP_CLIENT_ID=...
MP_CLIENT_SECRET=...
MP_WEBHOOK_SECRET=...
MP_TOKEN_KEY=...   # 32 bytes al azar, para cifrar los tokens de los boliches

  2. Migración 010_pagos.sql backend

    Tabla para la cuenta conectada de cada organización:

    create table payment_accounts (
  organization_id uuid primary key references organizations (id) on delete cascade,
  provider        text not null default 'mercadopago',
  mp_user_id      bigint not null,
  access_token    text not null,   -- cifrado (AES-256-GCM con MP_TOKEN_KEY)
  refresh_token   text not null,   -- cifrado
  public_key      text,
  live_mode       boolean not null,
  expires_at      timestamptz not null,
  connected_at    timestamptz not null default now()
);
alter table orders add column mp_preference_id text;

  3. Botón "Conectar Mercado Pago" en el panel del cliente dashboard

    • Ruta /api/mp/oauth/start: genera un state al azar, lo guarda en una cookie httpOnly y redirige a: 
      https://auth.mercadopago.com/authorization
  ?client_id=MP_CLIENT_ID
  &response_type=code
  &platform_id=mp
  &state=STATE
  &redirect_uri=https://www.nightowl.com.ar/api/mp/oauth/callback
    • Ruta /api/mp/oauth/callback: verifica que state coincida con la cookie y canjea el code (vale 10 minutos): 
      POST https://api.mercadopago.com/oauth/token
{
  "client_id": "...",
  "client_secret": "...",
  "grant_type": "authorization_code",
  "code": "TG-...",
  "redirect_uri": "https://www.nightowl.com.ar/api/mp/oauth/callback",
  "test_token": "true"          // en sandbox; "false" en producción
}
    • Guardar access_token, refresh_token, user_id, public_key y expires_in (≈ 180 días) en payment_accounts, cifrados.
    • Solo el dueño del cliente (o el admin con "Editar como el cliente") puede conectar o desconectar. Auditar las dos acciones.
    • El panel muestra "Conectado como …" y el botón Desconectar.

  4. Pagar: crear la preferencia y redirigir checkout

    payAction deja de llamar a simulatePayment (que queda solo para desarrollo) y crea una preferencia con el token del boliche:

    POST https://api.mercadopago.com/checkout/preferences
Authorization: Bearer <access_token del boliche>
{
  "items": [{ "title": "Entradas · Nombre del evento", "quantity": 1,
              "unit_price": order.total, "currency_id": "ARS" }],
  "payer": { "email": order.buyerEmail, "name": order.buyerName },
  "external_reference": order.id,
  "marketplace_fee": order.commissionAmount,
  "notification_url": "https://www.nightowl.com.ar/api/webhooks/mercadopago?org=ORG_ID",
  "back_urls": {
    "success": "https://SLUG.nightowl.com.ar/compra/TOKEN",
    "failure": "https://SLUG.nightowl.com.ar/compra/TOKEN",
    "pending": "https://SLUG.nightowl.com.ar/compra/TOKEN"
  },
  "auto_return": "approved",
  "binary_mode": true,
  "expires": true,
  "expiration_date_to": order.expiresAt,
  "payment_methods": { "excluded_payment_types": [{ "id": "ticket" }, { "id": "atm" }] },
  "statement_descriptor": "NOMBRE BOLICHE"
}
    • Guardar id en orders.mp_preference_id y redirigir al init_point.
    • Si la orden ya tiene preferencia y sigue vigente, reutilizarla (evita crear una por cada clic).
    • Mandar un header X-Idempotency-Key con el id de la orden.

  5. Webhook POST /api/webhooks/mercadopago backend

    • Validar la firma. El header x-signature trae ts=…,v1=…. Armar el texto y comparar con HMAC-SHA256 usando MP_WEBHOOK_SECRET: 
      manifest = `id:${dataId};request-id:${xRequestId};ts:${ts};`
esperado = hmacSha256Hex(MP_WEBHOOK_SECRET, manifest)
// comparar con v1 usando timingSafeEqual; dataId en minúsculas si es alfanumérico
      El formato del manifest no figura en la página de webhooks que leí: confirmarlo contra la referencia o el SDK oficial antes de programarlo.
    • Responder 200 enseguida: Mercado Pago espera 22 segundos y, si no, reintenta cada 15 minutos. El trabajo pesado va después (after()).
    • Con type = payment: consultar GET /v1/payments/{data.id} con el token del boliche (el de ?org=). Nunca confiar en el contenido del aviso.
    • Si status = "approved": 
      confirmPayment(db, {
  orderId: payment.external_reference,
  provider: "mercadopago",
  reference: String(payment.id),
  amount: payment.transaction_amount,
})
      y si devuelve "paid", mandar el email con las entradas (igual que hoy en payAction).
    • Si devuelve "refund_pending": el pago llegó tarde y ya no hay lugar. Ver paso 7.
    • Con type = mp-connect (desvinculación): marcar la cuenta como desconectada y cerrar la venta de ese cliente.

  6. Página de vuelta /compra/[token] checkout

    • Al volver con payment_id en la URL, consultar ese pago a Mercado Pago (no creerle a la URL) y, si está aprobado, llamar a confirmPayment. Así el comprador ve sus entradas aunque el webhook se atrase. Como confirmPayment ignora los avisos repetidos, no importa cuál llegue primero.
    • Si todavía no hay confirmación: mostrar "Estamos confirmando tu pago…" y refrescar cada pocos segundos.
    • Rechazado: "El pago no se aprobó" + botón para reintentar mientras la reserva siga vigente.

  7. Devoluciones backend

    • Para las órdenes en refund_pending: POST /v1/payments/{id}/refunds con el token del boliche (sin body = devolución total).
    • Al principio, devolver automático solo los pagos tardíos; las demás devoluciones las hace el boliche desde Mercado Pago.
    • Escuchar contracargos (evento de chargebacks) para anular las entradas afectadas.
    No está confirmado si en una devolución total Mercado Pago también devuelve el marketplace_fee de Nightowl. Probarlo en el sandbox.

  8. Renovar los tokens cron

    • Cron diario de Vercel: los tokens que vencen en menos de 30 días se renuevan con grant_type=refresh_token en POST /oauth/token.
    • Si la renovación falla, avisar por email al dueño del cliente y a los admins para que vuelva a conectar.

  9. Encender la venta checkout

    • checkoutEnabled deja de depender de NODE_ENV: un cliente vende si tiene Mercado Pago conectado y no está suspendido.
    • Si no tiene cuenta conectada, el público sigue viendo "Entradas muy pronto".

  10. Probar en sandbox y salir a producción entre los dos

    • Conectar el usuario de prueba vendedor desde el panel.
    • Comprar con el usuario de prueba comprador y tarjetas de prueba: aprobado, rechazado, reserva vencida.
    • Ver que llega el webhook, se emiten las entradas, llega el email y el QR se escanea.
    • Reenviar el mismo webhook dos veces: no se duplica nada.
    • Pagar con la reserva vencida y los lugares ya vendidos: la orden queda en refund_pending y se devuelve.
    • Ver en la cuenta de prueba de Nightowl que entró el marketplace_fee.
    • Probar una devolución total y ver qué pasa con la comisión.
    • Activar las credenciales de producción de la app y conectar el primer boliche real.

Para tener en cuenta

  • Comisión de Mercado Pago: depende del plazo de acreditación que elija el boliche en su cuenta. Mercado Pago la descuenta primero y nuestra comisión sale de lo que queda.
  • Seguridad: los tokens de los boliches van cifrados, nunca al navegador y nunca en logs.
  • Más procesadores: dejar el cobro detrás de una interfaz chica (createCheckout, getPayment, refund) para sumar Payway o Mobbex después.
  • Facturación: Nightowl factura su comisión y cada boliche sus entradas. Validar con el contador.
  • Antes de escribir los route handlers, leer la guía de Next 16 en node_modules/next/dist/docs/ (lo pide AGENTS.md).
